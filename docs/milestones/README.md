- **2026-10-21** — Fix: remote client lost a 5-minute dictation over a lossy Tailscale link. The live upload is one long POST; when sends stalled the client waited out its 600 s socket timeout, then failed (the server had already dropped its partial copy; only the local spool file survived). Now `ServerUpload` raises `UploadStalled` when audio waits in the queue for more than 30 s without the connection taking it, and the client resends the saved spool file automatically (`send_recording`: 3 attempts, 3 s × attempt back-off, only on connection/timeout errors). `-f` uploads get the same retries. Tests first (4 new, 216 pass). Not done yet: upload in closed chunks, each retried on its own (per-chunk acknowledgement and resume), which is the robust fix; belongs with the chunked-capture work.
- **2026-10-25** — Fix: a 3-minute remote dictation hung about 10 min, then failed with `Read timed out` and was not resent. Cause: the 2026-10-21 stall check only sees audio waiting in the client's queue, but the kernel send buffer (up to 4 MB, about 2 min of audio) takes the whole recording, so a link that dies near or after the stop goes unnoticed until the 600 s read timeout; and only `UploadStalled` triggered the resend. Fix in two parts. **Server:** `/transcribe` takes a `recording_id` (validated, not passed to whisper); `GET /result/<id>` answers `receiving` (with bytes received), `processing`, `done` (with the result, kept in `<base_dir>/.results/<id>.json`) or `unknown` (404); posting an id that is already `done` returns the stored result without transcribing again. **Client:** the live upload is named `<hostname>-<spool stem>`; after stop it waits 30 s (`ANSWER_WAIT`) for the answer, then `recover()` asks the server: `done` is delivered; `processing` and a growing `receiving` count are waited for; `unknown`, or no progress for 30 s, resends the spool (3 attempts). A resend that times out while the server works is not sent again. `-f` uses the same path: a spool file keeps its live id (so resending finds the first result), other files get a content hash id. Tests first (15 new, 233 pass), plus a real-HTTP check through a proxy that swallows the reply: the result came back by id 3 s after `ANSWER_WAIT`, with one workspace. Still to do from the same diagnosis: the server gives up on an upload with no data for 60 s; the phone page (an error overwritten by "Processing…", no `onclose`, no local copy, `EOF` sent before the last piece); restart `parec` if it dies mid-recording. `api._transcribe_via_server` (`answer -f` on a client) still uses plain `upload_file`.
- **2026-10-25** — Cause of the remaining remote failures found: an **MTU black hole**. From the hotel (WSL client, Tailscale direct path to the 4G host) pings through Tailscale passed up to 1216-byte packets and lost everything above, while `tailscale0` has MTU 1280. Small replies (`/health`, a status `unknown`) worked; anything longer stalled after the headers (`/result/<id>`: 200, then 0 of 6670 body bytes in 60 s), and so did uploads, so all three resends failed although the server had transcribed the live upload. Forcing 1100-byte TCP segments made the same request finish in 0.1 s; 1200 stalled. Fixes: (1) user lowered `tailscale0` MTU on the host; `configs/systemd/tailscaled-mtu.conf` is a `tailscaled` drop-in that sets 1200 at every start. (2) `client/net.py`: every client request (health, live upload, status, resend) uses a session that asks for 1100-byte TCP segments (`TCP_MAXSEG`, which caps both directions); `DICTATION_TCP_MSS` changes it, 0 turns it off. (Patching `urllib3`'s `default_socket_options` after import has no effect; it must go through the adapter's pool manager.) (3) Resends now run in the background (`BackgroundUpload`, 600 s read timeout) while `recover()` keeps asking the server; a resend whose own bytes are still moving counts as progress, so status checks failing on a bad link no longer trigger another resend. Before, a resend waited only 30 s after its last bytes were handed to the kernel (up to 4 MB still in flight), then hung up mid-upload, and the server threw its copy away. Tests first (5 new, 238 pass, the size cap checked on a real socket). Verified: `-f` on the failed 8.5-min spool fetched the stored result by id in 3.3 s.
