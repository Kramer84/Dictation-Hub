# Base of Truth: Structured Outputs in Ollama

This document serves as a comprehensive reference manual for the engineering of prompts, design of schemas, and selection of models to achieve reliable structured outputs using Ollama.

---

## 1. Core Architecture & Constrained Generation Mechanism

Structured outputs are executed in Ollama through strict structural enforcement rather than post-generation parsing or regular expression filtering.

* **Grammar-Based Next Token Selection (GBNF):** Ollama utilizes the `llama.cpp` grammar engine. When a JSON schema is provided via the `format` parameter, a strict formal grammar is constructed to govern token generation.
* **Logit Manipulation and Masking:** During the sampling stage of text generation, probabilities (logits) are calculated for potential next tokens. Any token violating the active JSON schema grammar at that specific position is masked (forbidden by setting its probability to zero). 
* **Model Context Awareness:** The underlying language model is not explicitly aware that its output space is being constrained via logit manipulation. However, once the initial structural characters (such as `{`) are generated by the enforced constraint, this syntax is injected into the model's own context history, naturally guiding the generation of subsequent valid JSON fields.
* **Performance Velocity:** Response times for structured generation are frequently faster than raw text generation. This acceleration occurs because the generation of conversational filler, introductory prose, and extraneous padding tokens is mechanically prevented.

---

## 2. Model Compatibility & Selection Criteria

Model architectures demonstrate varying levels of stability when subjected to strict structural constraints. 

### Performance Tiering
* **High-Reliability Architectures:** Models fine-tuned explicitly for tool use and function calling exhibit the highest accuracy. The **Qwen** family (e.g., `qwen2.5-coder`) and the **Llama** family (e.g., `llama3.1`, `llama3.2`) are optimized for structured data and maintain stable reasoning capacities under GBNF constraints.
* **Variable-Reliability Architectures:** The **Gemma** and **Phi** families have been observed to exhibit degradation in instruction-following capability or increased inconsistency when strict structural formatting is enforced on complex classes.
* **Scale Considerations:** Standard local models under 3B parameters generally demonstrate poor compliance with complex schema constraints unless specialized training has been applied.

### The Reasoning Model Contradiction (e.g., DeepSeek-R1)
A technical conflict exists when native structural constraints are applied to reasoning models like `deepseek-r1`. These models require an unconstrained output space to generate an internal reasoning trace (typically enclosed within `<think>` tags) prior to producing a final answer. If an Ollama JSON schema constraint is enforced at the API level, the GBNF grammar immediately masks the `<think>` token because it does not match the opening character of a JSON object (`{`). The reasoning capabilities of the model are thus short-circuited, resulting in immediate failure or severely degraded output quality.

---

## 3. GPU Resource Constraints (< X Gigabytes)

When execution is restricted to hardware environments with small GPUs containing less than X gigabytes of VRAM (e.g., limited to a total of 8 GB VRAM or less), specific structural strategies must be deployed:

* **VRAM Overhead Accounting:** System display servers (e.g., Xorg, Gnome) and active browser processes typically consume between 500 MB and 1 GB of VRAM, reducing the effective memory available for the local LLM server.
* **Quantized Model Selection:** Under strict VRAM limits, models must fit completely within the remaining hardware headroom to avoid spilling into system RAM, which causes catastrophic token generation delays. Compact models optimized for tool-use, such as `llama3.2` (approx. 2.0 GB) or `qwen2.5-coder:7b-instruct` (approx. 4.7 GB), are prioritized.
* **Sequential Offloading via Ultra-Small Models:** For memory-intensive tasks, a two-stage sequential pipeline is deployed to conserve VRAM:
    1. A larger or unconstrained model is executed to generate raw text or reasoning traces.
    2. The resulting text is post-processed using an ultra-small, specialized formatting model—such as **Osmosis-Structure-0.6B** (requiring only 1.2 GB of space)—to perform the final JSON structuring without overloading the GPU.

---

## 4. Schema Design Principles (Pydantic)

The programmatic definition of the schema directly impacts the data extraction accuracy of the local model.

* **Semantic Field Descriptions:** Semantic annotations must be embedded within the fields of Pydantic models. Because the Pydantic model is converted into a JSON schema and passed to the model context, these descriptions function as targeted instructions for individual keys.
* **Structural Simplicity:** Flat or moderately nested JSON structures are processed with higher fidelity than deep hierarchical trees. Recursive schemas or complex abstract syntax trees (ASTs) frequently result in processing failures on local models under 14B parameters.
* **Preamble Suppression:** The enforcement of a structural format implicitly eliminates conversational fluff (e.g., *"Sure, here is the data:"*), ensuring optimal utilization of the context window.

---

## 5. Prompt Engineering Tactics

Optimal data extraction requires alignment between the natural language prompt and the rigid structural formatting constraint.

### Explicit Formatting Anchors
Relying solely on the API `format` parameter can lead to data omission. Direct instructions, such as `"Respond in minified JSON"` or `"Return only valid JSON matching the requested schema"`, must be appended to the prompt to align the unconstrained internal probabilities of the model with the external GBNF boundaries.

### Schema-Embedded Chain-of-Thought (CoT)
To preserve reasoning capabilities within strict JSON constraints, analytical steps are engineered directly into the schema fields. Crucially, these reasoning fields must be declared *before* the target extraction fields so that the analytical tokens are generated first, populating the context window with the necessary logical history.

### Error Handling and Determinism
* **Temperature Control:** The `temperature` parameter is uniformly set to `0` for structured extraction tasks to enforce deterministic token selection based on maximum probability.
* **Robust Parsing:** Error handling strategies, such as wrapping the LLM call function with retry utilities (e.g., the `tenacity` library), are implemented to handle exceptional parsing failures.

## 6. Complete Implementation Examples

### Standard Data Extraction (Python)

Below is a complete script demonstrating the extraction of structured objects from natural language text using Pydantic validation and the Ollama Python library.

```python
from typing import List, Optional
from pydantic import BaseModel, Field
import ollama

# Schema definition with semantic descriptions
class Pet(BaseModel):
    name: str = Field(..., description="The given name of the pet animal.")
    animal: str = Field(..., description="The species of the animal, e.g., cat, dog.")
    age: int = Field(..., description="The age of the animal in years.")
    color: Optional[str] = Field(None, description="The primary color of the animal's fur or coat.")
    favorite_toy: Optional[str] = Field(None, description="The toy the animal prefers playing with most.")

class PetList(BaseModel):
    pets: List[Pet] = Field(..., description="A compiled list of all pets identified in the source text.")

def extract_pet_data() -> Optional[PetList]:
    source_text = """
    I have two pets.
    A cat named Luna who is 5 years old and loves playing with yarn. She has grey fur.
    I also have a 2 year old black cat named Loki who loves tennis balls.
    """

    prompt = f"Extract all pet entities from the text below. Respond in minified JSON matching the expected schema structure.\n\nText: {source_text}"

    try:
        # Execution of the structured chat call
        response = ollama.chat(
            model='qwen2.5-coder:7b-instruct',
            messages=[
                {
                    'role': 'user',
                    'content': prompt,
                }
            ],
            format=PetList.model_json_schema(),
            options={'temperature': 0}
        )

        # Validation and parsing of the response content
        validated_data = PetList.model_validate_json(response.message.content)
        return validated_data

    except Exception as e:
        print(f"An error occurred during extraction or validation: {e}")
        return None

if __name__ == "__main__":
    extracted_pets = extract_pet_data()
    if extracted_pets:
        print(repr(extracted_pets))
```

### Schema-Embedded Reasoning Pipeline (Python)

Below is an execution pattern designed for complex comparative analysis, ensuring reasoning tokens are generated prior to the final evaluation field.

```python
from pydantic import BaseModel, Field
import ollama

class TextComparison(BaseModel):
    # Reasoning field placed first to establish context tokens
    semantic_analysis: str = Field(
        ..., 
        description="A detailed step-by-step analysis comparing the core meanings, subtle differences, and implications of Text A and Text B."
    )
    # Target extraction field placed last
    meaning_is_retained: bool = Field(
        ..., 
        description="Set to True strictly if Text B retains the exact core meaning of Text A without loss of vital information. Set to False if the meaning is altered."
    )

def execute_comparison() -> Optional[TextComparison]:
    text_a = "The project must be completed by Friday afternoon to ensure compliance with the client SLA."
    text_b = "To fulfill the agreement with the client, the project needs to be finalized before Friday ends."

    prompt = (
        f"Analyze the two texts provided below. Fill out the semantic_analysis field thoroughly "
        f"before determining the final boolean verdict.\n\n"
        f"Text A: {text_a}\n"
        f"Text B: {text_b}\n\n"
        f"Respond strictly in minified JSON format."
    )

    try:
        response = ollama.chat(
            model='qwen2.5-coder:7b-instruct',
            messages=[
                {
                    'role': 'user',
                    'content': prompt,
                }
            ],
            format=TextComparison.model_json_schema(),
            options={'temperature': 0}
        )

        result = TextComparison.model_validate_json(response.message.content)
        return result
    except Exception as e:
        print(f"Parsing failed: {e}")
        return None

if __name__ == "__main__":
    comparison_result = execute_comparison()
    if comparison_result:
        print(comparison_result.model_dump_json(indent=2))
```

### Post-Processing Architecture via Specialized Small Models (Osmosis)

For workflows where formatting must be separated from inference to accommodate reasoning traces or reduce memory pressure on large models, a specialized processing pipeline using **Osmosis-Structure-0.6B** is employed. This model is trained via reinforcement learning specifically to map unstructured text into clean schemas.

```python
from pydantic import BaseModel, Field
import ollama

class FinalAnswer(BaseModel):
    answer: int = Field(..., description="The final calculated integer answer derived from the reasoning trace.")

def post_process_reasoning() -> Optional[FinalAnswer]:
    # Unstructured text containing reasoning steps, such as an output from a reasoning model
    unstructured_reasoning_trace = """
    Problem: Solve for x in the equation 2x + 5 = 13

    Let me work through this step by step:
    First, I need to isolate the term with x. I'll subtract 5 from both sides:
    2x + 5 - 5 = 13 - 5
    2x = 8

    Next, I'll divide both sides by 2 to solve for x:
    2x ÷ 2 = 8 ÷ 2
    x = 4

    Let me verify this answer by substituting back into the original equation:
    2(4) + 5 = 8 + 5 = 13 ✓

    Ok, which means I got the correct answer, and I'm confident about my answer.
    """

    # The system prompt communicates the schema configuration to the structural post-processor
    system_instruction = (
        f"You are a helpful assistant that understands and translates text to JSON format "
        f"according to the following schema. {FinalAnswer.model_json_schema()}"
    )

    try:
        response = ollama.chat(
            model='Osmosis/Osmosis-Structure-0.6B',
            messages=[
                {
                    'role': 'system',
                    'content': system_instruction
                },
                {
                    'role': 'user',
                    'content': unstructured_reasoning_trace,
                }
            ],
            format=FinalAnswer.model_json_schema(),
            options={'temperature': 0}
        )

        parsed_output = FinalAnswer.model_validate_json(response.message.content)
        return parsed_output
    except Exception as e:
        print(f"Structural formatting model failed: {e}")
        return None

if __name__ == "__main__":
    structured_target = post_process_reasoning()
    if structured_target:
        print(f"Parsed Structure: {structured_target}")
```
